Раздел 04 · Среда выполнения и отображения

Браузеры: как веб-страница становится приложением

Разберём браузер как программную платформу: от адресной строки и сетевого запроса до DOM, CSSOM, исполнения JavaScript, компоновки, отрисовки пикселей и защиты пользователя. Отдельно посмотрим, как разработчик исследует всё это через DevTools.

1. Что такое браузер

Веб-браузер — приложение, которое получает веб-ресурсы, интерпретирует документы и код, отображает интерфейс и предоставляет веб-страницам контролируемый доступ к возможностям устройства.

Браузер — не просто «окно для HTML». Это сложная система, объединяющая пользовательский интерфейс, сетевой стек, механизмы хранения, движки обработки веб-стандартов, графическую подсистему и средства безопасности.

Получение данных

URL, DNS, HTTP(S), кэш, соединения, загрузка документов и ресурсов.

Обработка страницы

HTML, CSS, JavaScript, DOM, layout, paint и вывод изображения.

Среда приложения

События, хранилища, мультимедиа, сеть, разрешения и безопасность.

Главное различие: браузер — это целое приложение и платформа; браузерный движок — лишь одна из его частей. Движок не обязан отвечать за адресную строку, историю, менеджер загрузок, синхронизацию или все сетевые функции браузера.

Для веб-разработчика браузер одновременно является средой исполнения и конечной целью: код должен соответствовать стандартам, корректно работать на разных устройствах и не предполагать, что у каждого пользователя одна и та же реализация.

2. Браузер, движок отображения и JavaScript-движок

Внутри браузера можно выделить несколько крупных частей. Их границы и названия зависят от реализации, но концептуально полезно различать три уровня.

Браузерное приложение

Вкладки, адресная строка, меню, история, закладки, загрузки, профиль, настройки и управление процессами.

Движок отображения

Разбирает HTML и CSS, строит DOM и CSSOM, рассчитывает стили, геометрию и формирует изображение страницы.

JavaScript-движок

Разбирает, компилирует и исполняет JavaScript, управляет памятью и сборкой мусора.

Например, движок отображения может предоставлять объекты DOM, а JavaScript-движок исполняет код, который обращается к ним. Но DOM API не является частью ядра языка ECMAScript: это интерфейс браузерной среды, связанный с HTML-движком.

Не путай: Array, Map, Promise — встроенные возможности языка JavaScript. document, window, fetch(), localStorage — браузерные API, которые среда предоставляет JavaScript-коду.

Браузеры могут использовать разные движки. От этого зависят поддержка веб-стандартов, особенности реализации, ошибки отображения и доступные инструменты.

Это полезная базовая карта, но не универсальная таблица для всех устройств и выпусков. У одного бренда могут быть разные платформенные сборки, а мобильные платформы и правила распространения браузеров могут накладывать дополнительные ограничения.

3.1. Почему движки важны

  • Новый CSS API может уже поддерживаться одним движком и ещё не поддерживаться другим.
  • Различия могут проявляться в деталях шрифтов, форм, прокрутки, видео и системных элементов.
  • Оптимизации и внутренние алгоритмы рендеринга могут отличаться.
  • Баг может быть связан с конкретным движком, версией браузера, операционной системой или видеодрайвером.
Практический вывод: проверяй возможности по конкретной функции, а не по общему впечатлению «браузер современный». Для этого подходят MDN Browser Compatibility Data и Can I Use.

4. Архитектура браузера: процессы и потоки

Современные браузеры обычно используют многопроцессную архитектуру. Вместо того чтобы выполнять всю работу в одном процессе, они разделяют разные типы задач между процессами и потоками. Это повышает устойчивость и помогает ограничивать доступ веб-контента к системе.

4.1. Что такое процесс и поток

Процесс — выполняющийся экземпляр программы с собственным адресным пространством и ресурсами. Поток — последовательность выполнения внутри процесса. Один процесс может иметь несколько потоков, которые выполняют разные задачи.

КомпонентТипичная ответственность
Browser processПользовательский интерфейс браузера, вкладки, навигация, управление другими процессами и часть системных интеграций.
Renderer processОбработка веб-страницы: HTML/CSS, DOM, выполнение JavaScript, layout и подготовка визуального результата.
Network service/processСетевые операции и получение ресурсов. Конкретная реализация может быть отдельным процессом или набором служб.
GPU processКоординация операций с графическим оборудованием, композитинг и ускоренные графические пути.
Utility processВспомогательные изолированные задачи — например, обработка отдельных типов данных.

4.2. Почему не обязательно один процесс на вкладку

Распространённая схема «каждая вкладка — отдельный процесс» является упрощением. Браузер может группировать документы по сайтам, использовать несколько процессов для одного сложного сайта или повторно использовать процессы в пределах своих правил. На распределение влияют Site Isolation, память, тип документа и реализация конкретного браузера.

4.3. IPC

Когда разные процессы должны обменяться данными, используется IPC (Inter-Process Communication). Например, renderer может запросить загрузку ресурса, а браузерный или сетевой процесс выполняет запрос и возвращает результат. IPC требует формализованных сообщений и проверок, поскольку граница процесса — также важная граница безопасности.

Зачем это разработчику? Если JavaScript завис в одном renderer-процессе, браузерное окно и другие вкладки не обязательно должны полностью зависнуть вместе с ним. Многопроцессность помогает изоляции, но не делает приложение неуязвимым к чрезмерной нагрузке.

5. Что происходит, когда пользователь открывает URL

Ввод адреса в адресную строку запускает цепочку действий. Ниже — учебная модель типичной навигации. Некоторые этапы могут быть пропущены благодаря кэшу, Service Worker, уже открытому соединению или другим механизмам.

5.1. Разбор адреса

URL содержит схему (например, https), имя хоста, необязательный порт, путь, query-параметры и фрагмент. Фрагмент после # обычно обрабатывается на стороне документа и сам по себе не отправляется серверу в HTTP-запросе.

5.2. Проверка кэша и Service Worker

Браузер может использовать свежий HTTP-кэш и не обращаться к сети за некоторыми ресурсами. Если у сайта зарегистрирован Service Worker и он управляет текущим запросом, его обработчик может вернуть заранее сохранённый ответ, выполнить сетевой запрос или собрать ответ из нескольких источников.

5.3. Получение ответа

Браузер получает HTTP-ответ: статус, заголовки и тело. Ответ может быть HTML-документом, JSON, изображением, CSS, JavaScript или другим типом ресурса. Заголовки влияют на кэширование, тип содержимого, безопасность, cookies и дальнейшую обработку.

После поступления первых частей HTML браузер обычно может начать разбор, не дожидаясь скачивания всего документа. Поэтому загрузка, парсинг и получение зависимых ресурсов частично перекрываются.

6. Сетевой стек: DNS, соединения, TLS и HTTP

Веб-страницы редко состоят из одного файла. HTML может ссылаться на таблицы стилей, скрипты, изображения, шрифты, видео и API. Браузер организует получение этих ресурсов через сетевые механизмы.

6.1. DNS

DNS (Domain Name System) помогает сопоставить доменное имя, например example.com, с сетевыми адресами. Результат может быть взят из кэша браузера, ОС, локальной сети или получен через DNS-резолвер. Поэтому DNS-запрос не обязательно выполняется при каждом обращении к сайту.

6.2. Транспорт и защищённое соединение

  • TCP — транспортный протокол с установлением соединения, который используется, например, HTTP/1.1 и HTTP/2.
  • TLS — протокол защиты соединения: шифрование, проверка подлинности сервера и целостности данных.
  • QUIC — транспортный протокол поверх UDP, используемый HTTP/3; защита интегрирована через TLS 1.3.

Не следует представлять все современные соединения как одну схему «TCP, затем TLS». Выбор зависит от версии HTTP, доступности протокола, сетевых условий и возможностей сервера и клиента.

6.3. HTTP

HTTP задаёт формат запросов и ответов между клиентом и сервером. В запросе есть метод, целевой ресурс, заголовки и, при необходимости, тело. В ответе — статус, заголовки и тело.

МетодТипичное назначение
GETПолучить представление ресурса.
POSTПередать данные для обработки или создания ресурса.
PUTСоздать или заменить представление ресурса по заданному адресу.
PATCHЧастично изменить ресурс.
DELETEУдалить ресурс.
HEADПолучить заголовки без тела ответа.

Браузер использует HTTP не только для HTML. Запросы к API, картинки, стили, скрипты и шрифты также могут загружаться по HTTP(S).

6.4. Кэширование HTTP

Заголовки Cache-Control, ETag, Last-Modified и другие позволяют браузеру сохранять ответы и определять, можно ли использовать их повторно или нужно проверить актуальность на сервере.

Практический навык: вкладка Network в DevTools показывает URL, метод, статус, тип ресурса, время, объём передачи, инициатор и заголовки запроса/ответа. Это первый инструмент для разбора «почему файл не загрузился».

7. Разбор HTML и построение DOM

HTML-парсер превращает полученные байты в структуру документа. В учебной модели можно выделить декодирование символов, токенизацию и построение дерева узлов. Реальная реализация устроена сложнее и должна обрабатывать ошибочную разметку по правилам HTML.

<main>
  <h1>Каталог</h1>
  <article>
    <p>Описание товара</p>
  </article>
</main>

7.1. Почему DOM — не просто исходный текст

DOM — дерево объектов. Оно может содержать узлы, созданные браузером при обработке документа, и позднее изменяться скриптами. Изменение DOM через JavaScript не переписывает HTML-файл на сервере.

7.2. Парсер и скрипты

Классический внешний скрипт без async или defer может приостановить разбор HTML, чтобы быть загруженным и выполненным в нужном порядке. Скрипты с defer выполняются после разбора документа, а async — когда загрузка завершена, без гарантии порядка относительно других async-скриптов. Модульные скрипты имеют собственные правила загрузки и обычно откладываются до завершения разбора документа.

7.3. Preload scanner

Современные браузеры могут использовать вспомогательное предварительное сканирование разметки, чтобы заранее обнаруживать ресурсы вроде изображений, стилей и скриптов, пока основной парсер занят. Это помогает эффективнее использовать сеть, но не отменяет правил блокировки и зависимостей.

Вывод: порядок скриптов и их атрибуты могут влиять на скорость появления содержимого. Не добавляй async или defer механически: сначала определи зависимости и требуемый порядок выполнения.
Углублённое изучение: отдельная глава HTML Parser — tokenizer, insertion modes и восстановление DOM разбирает нормативный алгоритм по шагам и содержит интерактивные лаборатории.

8. CSSOM, каскад и вычисление стилей

Параллельно с DOM браузер получает CSS: из внешних файлов, элемента <style>, атрибута style и пользовательских стилей. CSS-парсер разбирает правила и строит внутреннее представление таблиц стилей — CSSOM.

Для каждого элемента браузер определяет подходящие CSS-правила, применяет каскад и наследование и вычисляет итоговые значения свойств. В этот процесс входят происхождение правил, важность, слои каскада, специфичность и порядок объявления.

/* style.css */
.card {
  padding: 1rem;
  color: #172033;
}

.card.is-active {
  border-color: royalblue;
}

DOM сообщает, какие элементы существуют и как они вложены. CSSOM сообщает, какие правила могут применяться. На их основе браузер определяет визуальное представление элементов.

Важная оговорка: популярная модель «сначала полностью DOM, потом полностью CSSOM, и только потом экран» слишком линейна. Загрузка, парсинг и рендеринг могут частично перекрываться. При этом таблицы стилей способны задерживать первый рендер и выполнение некоторых скриптов, поэтому порядок ресурсов имеет значение.

9. Критический путь рендеринга: от DOM до пикселей

Рендеринг — преобразование структуры документа, стилей и геометрии в изображение, которое браузер выводит на экран.

9.1. Render tree

В классическом объяснении браузер объединяет DOM с вычисленными стилями и формирует структуру визуально отображаемого содержимого. Узлы, которые не участвуют в отображении, могут быть исключены из этой структуры. Например, элемент с display: none не создаёт обычного отображаемого блока; при visibility: hidden место в компоновке, как правило, сохраняется.

9.2. Layout (reflow)

Layout — расчёт геометрии: размеров и положения блоков, текста, изображений и других отображаемых объектов. На результат влияют размер viewport, шрифты, содержимое, CSS, прокрутка и правила компоновки.

Изменение ширины элемента, текста, структуры DOM или других факторов, влияющих на геометрию, может вызвать повторный layout. В DevTools такой перерасчёт часто называют reflow.

9.3. Paint, rasterization и compositing

Paint — подготовка операций рисования: текст, границы, фоны, тени, изображения и другие визуальные эффекты. Rasterization превращает графические команды в пиксели. Compositing объединяет подготовленные поверхности или слои в итоговый кадр.

Часть операций может использовать GPU, но не следует считать, что «весь CSS рисуется видеокартой». Решение о слоях и ускорении зависит от движка, свойств элементов, оборудования и текущего состояния страницы.

Для живого примера нужен включённый JavaScript. Код и пояснения показаны в блоках рядом.

9.4. Какие изменения дороже

Тип измененияЧто может потребоватьсяПример

Для живого примера нужен включённый JavaScript. Код и пояснения показаны в блоках рядом.

Это ориентир, а не безусловная гарантия. Например, тень может быть дорогой для отрисовки, а изменение свойства, которое кажется простым, может повлечь перерасчёт стилей или геометрии.

Оптимизируй по измерениям. Избегай лишних чтений геометрии между DOM-записями, которые вынуждают браузер синхронно пересчитывать layout. Группируй изменения и проверяй профиль в Performance.

10. Изображения, шрифты, видео и другие ресурсы

Для отображения страницы браузеру могут понадобиться ресурсы разных типов. У каждого типа есть этапы загрузки, декодирования, обработки и вывода.

Браузер может начать показывать часть страницы до загрузки всех второстепенных ресурсов. Но поздняя загрузка изображения или шрифта способна изменить геометрию контента и повлиять на визуальную стабильность.

11. JavaScript runtime внутри браузера

JavaScript-движок выполняет код, но браузерная среда предоставляет дополнительные механизмы: таймеры, события интерфейса, сетевые операции и очередь задач. Вместе они формируют модель выполнения JavaScript в браузере.

11.1. JavaScript-движок

Движок разбирает исходный код, может компилировать его в промежуточное или машинное представление, исполняет функции, управляет объектами в памяти и освобождает недостижимые объекты с помощью сборки мусора. Разные движки используют разные архитектурные решения и оптимизации.

11.2. Стек вызовов

При вызове функции создаётся контекст её выполнения, который добавляется в стек вызовов. Когда функция завершается, контекст снимается. Долгая синхронная функция удерживает поток выполнения и может задерживать обработку событий, обновление интерфейса и реакцию на ввод.

function first() {
  second();
}

function second() {
  console.log("Вызов завершён");
}

first();

11.3. Event Loop

Event Loop связывает выполнение JavaScript с очередями задач и возможностями браузера. Упрощённо: когда текущий синхронный код завершается, среда выбирает задачу из очереди; после выполнения задачи обрабатывает очередь микрозадач, а затем браузер при подходящей возможности может обновить отображение.

11.4. Задачи и микрозадачи

Обработчик таймера setTimeout обычно запускается как задача. Обработчики Promise.then() и функция, переданная в queueMicrotask(), попадают в очередь микрозадач. Микрозадачи обрабатываются после завершения текущего стека и до перехода к следующей задаче; длинная цепочка микрозадач способна отложить отрисовку.

console.log("A");

setTimeout(() => console.log("B — task"), 0);
Promise.resolve().then(() => console.log("C — microtask"));

console.log("D");

// Типичный порядок: A, D, C, B

11.5. requestAnimationFrame

requestAnimationFrame() просит браузер вызвать функцию перед следующей возможностью обновить кадр. Его удобно использовать для визуальных анимаций, синхронизированных с обновлением экрана. Он не является таймером точной длительности и не гарантирует фиксированную частоту кадров.

Главное: «JavaScript однопоточный» — упрощение, которое относится к обычному выполнению скриптов в конкретном контексте. Браузер сам многопоточен, а Web Workers позволяют выполнять JavaScript в отдельных потоках с отдельными глобальными контекстами.

document.addEventListener("DOMContentLoaded", () => {

14.1. Cookies и безопасность

Cookie может содержать идентификатор сессии. Важные атрибуты:

  • Secure — передавать cookie только по защищённому соединению (HTTPS).
  • HttpOnly — не предоставлять cookie через обычный JavaScript API document.cookie.
  • SameSite — ограничивать отправку cookie в некоторых cross-site сценариях и снижать риск CSRF.
  • Domain, Path, Expires и Max-Age — задавать область действия и срок хранения.

14.2. Квоты и очистка

Хранилища ограничены квотами, зависящими от браузера, платформы, свободного места и политики хранения. Пользователь может очистить данные сайта, браузер может удалять часть данных при нехватке места, а режим приватного просмотра меняет поведение хранения. Не проектируй приложение так, будто локальные данные никогда не исчезают.

15. Безопасность браузера и веб-приложений

Веб-страницы часто исполняют код из внешних источников и обрабатывают конфиденциальные данные. Браузер поэтому применяет модель происхождения, ограничения доступа, песочницы, разрешения и другие защитные механизмы.

15.1. Origin и Same-Origin Policy

Origin (источник) в типичном случае определяется тройкой:

scheme + host + port

https://shop.example:443
  └ схема: https
  └ хост: shop.example
  └ порт: 443

Same-Origin Policy (SOP) ограничивает взаимодействие документов и скриптов из разных источников. Например, страница на одном сайте не должна произвольно читать содержимое личного кабинета, открытого на другом сайте.

Сравнение источников:

URLСовпадает с https://example.com?Причина
https://example.com/pageДаСхема, хост и порт совпадают.
http://example.comНетДругая схема.
https://api.example.comНетДругой хост.
https://example.com:8443НетДругой порт.

Для живого примера нужен включённый JavaScript. Код и пояснения показаны в блоках рядом.

15.2. CORS

CORS (Cross-Origin Resource Sharing) — механизм, с помощью которого сервер через HTTP-заголовки сообщает браузеру, каким другим источникам разрешено читать определённые ответы. Это не способ отключить SOP в целом и не механизм аутентификации.

При некоторых запросах браузер сначала отправляет preflight-запрос методом OPTIONS, чтобы проверить, разрешает ли сервер фактический запрос с выбранными методом и заголовками. Preflight нужен не для каждого cross-origin запроса.

Для живого примера нужен включённый JavaScript. Код и пояснения показаны в блоках рядом.

Типичная ошибка: CORS — не проблема, которую правильно решать отключением защиты браузера. Обычно нужно настроить серверные заголовки и убедиться, что приложение действительно должно обращаться к этому origin.

15.3. CSP

Content Security Policy (CSP) — политика безопасности, которую сервер может передавать через HTTP-заголовок. Она ограничивает источники скриптов, стилей, изображений, подключений и других ресурсов. CSP помогает снизить последствия ряда атак, в том числе внедрения вредоносного кода, но требует корректной настройки.

Content-Security-Policy:
  default-src 'self';
  img-src 'self' https: data:;
  object-src 'none';
  base-uri 'self';

Это только иллюстрация синтаксиса, а не готовая политика для любого проекта. Реальный набор директив зависит от архитектуры сайта.

Для живого примера нужен включённый JavaScript. Код и пояснения показаны в блоках рядом.

15.4. Sandbox

Песочница ограничивает действия содержимого. Например, атрибут sandbox у iframe позволяет включать ограничения на скрипты, формы, навигацию, всплывающие окна и другие действия. Разрешения можно добавлять точечно, но комбинации флагов требуют осторожности.

15.5. Permissions и защищённые контексты

Камера, микрофон, геолокация, уведомления и другие чувствительные возможности регулируются разрешениями и правилами браузера. Многие API доступны только в secure context — обычно это HTTPS, а также некоторые локальные контексты разработки.

15.6. Site Isolation и sandbox процессов

Процессная изоляция старается разделить контент разных сайтов так, чтобы компрометация одной страницы не давала свободного доступа к памяти другой. Это не заменяет проверку данных и защиту самого сайта, но уменьшает последствия ошибок и атак.

15.7. Что должен делать разработчик

  • Передавать конфиденциальные данные только по HTTPS.
  • Не вставлять непроверенный пользовательский ввод в HTML как доверенную разметку.
  • Настраивать cookies для сессий с учётом Secure, HttpOnly и SameSite.
  • Использовать CSP и другие подходящие HTTP-заголовки.
  • Проверять данные и права доступа на сервере; браузерные ограничения не заменяют серверную защиту.
  • Запрашивать чувствительные разрешения только в понятном пользователю контексте.

16. Доступность и дерево доступности

Браузер формирует не только DOM для работы страницы, но и дополнительное представление интерфейса для вспомогательных технологий — дерево доступности (Accessibility Tree). Оно содержит сведения о роли, имени, состоянии и связях элементов.

Например, элемент <button>Сохранить</button> уже имеет нативную роль кнопки и доступное имя из текста. У обычного <div> такой семантики нет, даже если его визуально оформить как кнопку.

  • Семантический HTML помогает браузеру построить правильное дерево доступности.
  • Подписи форм связываются с полями через label и соответствующие атрибуты.
  • Клавиатурная навигация и видимый фокус важны для пользователей, не использующих мышь.
  • ARIA уточняет семантику, но не должна без необходимости заменять встроенные HTML-элементы.
  • Контраст, масштабирование, порядок фокуса и текстовые альтернативы нужно проверять отдельно.

В DevTools многих браузеров есть вкладка или панель Accessibility, где можно исследовать роли, доступные имена, состояния и структуру доступности.

17.1. Минимальный сценарий диагностики

  1. Открой страницу и проверь Console на ошибки.
  2. В Network перезагрузи страницу и найди запросы с ошибочными статусами.
  3. В Elements выбери проблемный элемент и проверь computed styles.
  4. В Sources поставь breakpoint и повтори действие пользователя.
  5. В Performance запиши профиль взаимодействия, если страница тормозит.
  6. В Application проверь кэш и хранилища, если приложение показывает устаревшие данные.

У Firefox есть собственные Developer Tools, а Safari предоставляет Web Inspector. Названия панелей и детали интерфейса могут отличаться, но основные задачи отладки похожи.

18. Производительность: что измерять

Быстродействие — не только скорость загрузки HTML. Пользователь оценивает, когда появляется основной контент, как быстро интерфейс реагирует на действия и насколько стабильно располагаются элементы страницы.

18.2. Практические приёмы

  • Уменьшать объём критических ресурсов и не загружать ненужный JavaScript.
  • Использовать подходящие форматы и размеры изображений, задавать их геометрию.
  • Отложенно загружать изображения ниже первого экрана, когда это уместно.
  • Избегать длинных синхронных задач; делить тяжёлую работу на части или переносить подходящие вычисления в Worker.
  • Не вызывать синхронный layout многократно между чтением геометрии и записью стилей.
  • Не анимировать без необходимости свойства, которые постоянно меняют геометрию.
  • Проверять реальную производительность на медленных устройствах и сетях.
Не оптимизируй на глаз. Сначала зафиксируй профиль и найди узкое место. Иногда проблема в сети или сервере, иногда — в JavaScript, изображениях, layout или шрифтах.

19. Совместимость браузеров и веб-стандарты

Стандарты описывают ожидаемое поведение веб-платформы, а браузерные движки реализуют эти требования. Реализации развиваются не одновременно, а отдельные функции могут иметь ограничения или особенности.

19.1. Как проверять поддержку

  • MDN Browser Compatibility Data — таблицы совместимости конкретных HTML, CSS и JavaScript возможностей.
  • Can I Use — быстрый просмотр поддержки функций в разных браузерах и версиях.
  • Web Platform Tests — набор тестов, помогающий проверять соответствие реализаций веб-стандартам.
  • Реальные тесты — проверка целевых браузеров и устройств приложения.

19.2. Progressive Enhancement

Прогрессивное улучшение — подход, при котором базовое содержание и основные действия работают на надёжном фундаменте, а дополнительные возможности подключаются там, где они поддерживаются. Например, обычная HTML-форма может оставаться доступной, а JavaScript улучшает её валидацию и интерфейс.

19.3. Feature detection

Проверяй наличие конкретной функции, а не только название браузера.

if ("IntersectionObserver" in window) {
  // Использовать IntersectionObserver
} else {
  // Предусмотреть альтернативный сценарий
}

if (CSS.supports("display", "grid")) {
  // Браузер понимает указанное CSS-значение
}

Проверка наличия API не всегда означает, что все его детали реализованы одинаково. Для сложных функций нужны тесты и анализ совместимости.

20. Progressive Web Apps и офлайн-режим

Progressive Web App (PWA) — веб-приложение, которое использует ряд браузерных возможностей, чтобы приблизить пользовательский опыт к приложению: устанавливаемость на поддерживаемых платформах, работа с кэшем, офлайн-сценарии, интеграция с ОС и другие функции.

20.1. Основные составляющие

  • Web App Manifest — описание названия, иконок, стартового URL, режима отображения и других параметров приложения.
  • Service Worker — фоновый скрипт с отдельным жизненным циклом, который может обрабатывать события и перехватывать управляемые fetch-запросы.
  • Cache Storage — хранение ответов, которыми может управлять Service Worker.
  • HTTPS — обязательный или фактически необходимый защищённый контекст для многих функций PWA.

20.2. Пример идеи кэширования

// sw.js — упрощённый пример
self.addEventListener("install", event => {
  event.waitUntil(
    caches.open("app-v1").then(cache =>
      cache.addAll(["/", "/index.html", "/app.css"])
    )
  );
});

self.addEventListener("fetch", event => {
  event.respondWith(
    caches.match(event.request).then(cached =>
      cached || fetch(event.request)
    )
  );
});

Это демонстрация принципа, а не универсальная production-стратегия. В реальном проекте нужно управлять версиями кэша, обновлением файлов, ошибками сети, запросами API и удалением устаревших записей.

21. Практический рабочий процесс веб-разработчика

Браузер — не только место, где проверяют готовый сайт. Это ежедневная рабочая среда для разработки.

  1. Создать страницу. Подготовить HTML, CSS и JavaScript с понятной структурой.
  2. Открыть в браузере. Проверить реальное поведение, масштабирование и адаптивность.
  3. Изучить DOM и стили. В Elements/Inspector проверить структуру, вычисленные стили и box model.
  4. Проверить ошибки. В Console найти исключения, предупреждения и ошибки API.
  5. Проверить сеть. В Network найти неудачные запросы, CORS, неправильные MIME-типы и медленные ресурсы.
  6. Поставить breakpoint. В Debugger остановить выполнение и исследовать переменные и стек вызовов.
  7. Измерить производительность. Записать Performance profile и найти длинные задачи, лишний layout или paint.
  8. Проверить совместимость. Пройти ключевые сценарии в целевых браузерах и на мобильном устройстве.
Полезная привычка: формулируй проблему как наблюдаемый факт: «запрос /api/products вернул 403», «элемент получил computed width 0», «обработчик занимает 180 мс». Это гораздо эффективнее, чем «сайт сломан».

22. Практические задания

Задания идут от простых наблюдений к пониманию взаимодействия браузерных подсистем.

Задание 1. Проследи загрузку страницы
  1. Открой любой сайт и DevTools → Network.
  2. Включи Preserve log и перезагрузи страницу.
  3. Найди основной запрос типа Document.
  4. Посмотри status code, response headers, initiator и timing.
  5. Выбери CSS, JS, image и сравни типы запросов.

Цель: научиться понимать, какие файлы браузер получает и в каком порядке инициирует запросы.

Задание 2. Исследуй DOM и CSSOM
  1. Создай страницу с заголовком, абзацем и кнопкой.
  2. Открой Elements и найди соответствующие узлы DOM.
  3. Измени текст элемента через панель.
  4. Посмотри computed styles и измени одно CSS-свойство.
  5. Обнови страницу и проверь, какие изменения сохранились.

Цель: увидеть разницу между исходным документом, текущим DOM и применёнными стилями.

Задание 3. Исследуй Event Loop
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => {
  console.log("3");
});

queueMicrotask(() => console.log("4"));

console.log("5");

Предскажи порядок вывода, затем выполни код в Console. Объясни, почему синхронные команды, микрозадачи и timer task идут именно в таком порядке.

Задание 4. Найди причину медленного интерфейса
  1. Открой Performance и запиши взаимодействие со страницей.
  2. Найди длинные задачи на Main thread.
  3. Изучи вызванные ими функции и события Layout / Recalculate Style / Paint.
  4. Сформулируй гипотезу об узком месте.
  5. Измени код и сними профиль повторно.

Цель: отличать предположение от измеренного результата.

Задание 5. Проверь безопасность origin
  1. Открой страницу своего сайта и попробуй выполнить fetch к другому origin.
  2. Изучи сообщение об ошибке в Console.
  3. В Network посмотри preflight OPTIONS, если он был отправлен.
  4. Изучи заголовки CORS в ответе.

Цель: понять, что браузер ограничивает чтение cross-origin ответов, а разрешение задаётся сервером.

Задание 6. Проверь разные движки
  1. Открой один и тот же учебный проект в Chromium-браузере, Firefox и Safari (если доступен).
  2. Проверь сетку, шрифты, формы, фокус клавиатуры и прокрутку.
  3. Запиши отличия и проверь поддержку спорной функции.
  4. Исправь проблему стандартным способом, не привязываясь к user-agent без необходимости.

Цель: выработать привычку тестировать поведение, а не полагаться на один браузер.
