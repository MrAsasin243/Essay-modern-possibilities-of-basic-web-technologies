Layout Engine: как браузер рассчитывает геометрию

Layout — не команда «расставить HTML-элементы». Это семейство алгоритмов, которые получают структуру боксов, вычисленные стили и ограничения родительского контекста, а затем рассчитывают размеры и пространственные отношения. Результат должен работать для текста, разных письменностей, гибких контейнеров, сеток, прокрутки, печати и динамических изменений.

01 · INPUTS → CONSTRAINTS → GEOMETRY

Что именно делает Layout Engine

На входе layout-алгоритм получает не просто DOM. Ему нужны как минимум структура, вычисленные CSS-значения, правила конкретного formatting context, доступное пространство и данные о содержимом. На выходе появляются геометрические результаты, которые позднее используются для painting, hit-testing, прокрутки и некоторых DOM API.

DOM + generated contentЭлементы, текст, псевдоэлементы

Это концептуальная модель, а не обязательный список классов или отдельных проходов для всех браузеров. Реальные движки могут объединять стадии, кэшировать результаты и выполнять частичную компоновку.

Важные различия

A

Computed style

Это вычисленные значения CSS-свойств после каскада и наследования. Они задают параметры компоновки, но сами по себе ещё не являются окончательной геометрией. Например, width: auto не означает заранее известную числовую ширину.

B

Box tree / layout objects

Движок организует боксы и структуры, необходимые выбранным моделям компоновки. Эта структура не обязана повторять DOM один к одному: возможны anonymous boxes, отсутствие бокса и дополнительные боксы.

C

Fragment tree

Один логический бокс может дать несколько фрагментов: например, текстовый блок распадается на строки, а содержимое — на колонки или страницы. Геометрия результата может быть богаче, чем одна пара x/y и width/height.

Главная идея

Алгоритм компоновки не «угадывает пиксели из CSS». Он разрешает систему взаимозависимых ограничений: что доступно, что обязательно должно поместиться, что может растягиваться, что переносится и какие правила имеет текущий контекст.

02 · BOX GENERATION

DOM tree не равен box tree

DOM описывает документную структуру, с которой работают селекторы, события, accessibility и DOM API. CSS Display определяет, какие боксы создаются и как они участвуют в форматировании. Поэтому «элемент существует в DOM» и «элемент имеет собственный layout box» — разные утверждения.

Какие преобразования происходят

  • display: none исключает элемент и его поддерево из box tree для визуальной компоновки. DOM-узлы остаются в документе.
  • display: contents убирает principal box самого элемента, но сохраняет участие его потомков и псевдоэлементов в формировании боксов. Это не то же самое, что удаление узла из DOM.
  • display: inline, block, list-item, таблицы, flex и grid задают разные виды боксов и правила их участия в formatting contexts.
  • Anonymous boxes возникают, когда для корректной структуры форматирования нужен контейнер, которому не соответствует явный HTML-элемент. Такой бокс нельзя выбрать CSS-селектором как обычный DOM-элемент.
  • Псевдоэлементы ::before и ::after могут генерировать содержимое и боксы, хотя не являются обычными узлами DOM.

Пример anonymous box

<div class="flex">
  свободный текст
  <button>Кнопка</button>
</div>

При display: flex непосредственные flex items должны быть представлены как элементы flex-контейнера. Прямая текстовая последовательность оборачивается в anonymous flex item. Стилизовать саму эту анонимную обёртку отдельным селектором нельзя.

Почему это важно

Нельзя выводить структуру layout только из дерева Elements в DevTools. DOM-представление — не полная визуальная модель. Для отладки надо смотреть computed styles, box model, layout overlays и фактические фрагменты/позиции.

Нюанс доступности

display: contents в прошлом имел межбраузерные проблемы с сохранением семантики некоторых элементов в accessibility tree. Не применяй его как универсальный способ «развернуть обёртку» без проверки целевых браузеров и дерева доступности.

03 · FORMATTING CONTEXTS

Formatting context — локальная система правил

Formatting context определяет, как группа боксов размещается и взаимодействует с соседями. Это не обязательно отдельный процесс или поток. Это набор правил геометрии. Один документ одновременно содержит вложенные и взаимодействующие контексты.

Он может быть создан, например, flow-root, float, absolute positioning, overflow-контекстами и некоторыми другими механизмами.

Block flow и схлопывание margin

В обычном block flow вертикальные соседние margins некоторых блочных боксов могут схлопываться (margin collapsing). Итоговое расстояние не обязательно равно сумме двух заданных значений. Схлопывание зависит от контекста, положения margins, содержимого, borders/padding и того, образует ли элемент новый BFC.

Создание нового BFC меняет правила взаимодействия с floats и margin collapsing. Например, display: flow-root создаёт BFC без побочного эффекта прокрутки, который исторически использовали у overflow: hidden. Это один из примеров, когда CSS-свойство выбирают не ради внешнего вида, а ради границы форматирования.

Inline layout и текст

Для текста движок должен определить доступную ширину строки, сегменты переносов, метрики шрифтов, правила shaping и bidi. После этого последовательность inline items разбивается на line boxes. Внутренние фрагменты текста могут отличаться от границ HTML-узлов: строка способна включать часть одного текстового узла и части соседних inline-элементов.

Поэтому ширина текста не всегда вычисляется как сумма простых ширин символов. На неё влияют shaping (лигатуры и контекстные формы), кернинг, языковые правила переносов, Unicode bidirectional algorithm, letter/word spacing, font fallback и variable font axes.

Почему создают новый контекст

Граница formatting context изолирует часть правил взаимодействия. Например, BFC не даёт внешним floats проникать внутрь контекста и участвовать в его внутренней геометрии как обычным соседям. Flex и Grid заменяют обычный block/inline алгоритм для непосредственных items, но сами могут содержать обычный поток внутри своих items.

Не смешивай термины

display: block описывает тип principal box и его внешнее поведение. BFC описывает контекст компоновки. Блочный элемент не обязательно создаёт новый BFC, а некоторые элементы со значениями display, не похожими на block, способны создавать отдельные formatting contexts.

04 · CONTAINING BLOCKS & COORDINATE SYSTEMS

Containing block — откуда берутся проценты и координаты

Containing block — геометрическая система отсчёта, относительно которой разрешаются некоторые размеры и позиции. Это не обязательно ближайший DOM-parent. Правило зависит от типа бокса, позиционирования и свойств предков.

  • Для обычного статически позиционированного блочного бокса содержащий блок обычно образован content box ближайшего block container ancestor.
  • Для absolute-positioned элемента containing block обычно формируется padding box ближайшего подходящего positioned ancestor; дополнительные свойства вроде transform и некоторых containment-механизмов также могут создавать containing block для positioned descendants.
  • Для fixed-positioned элемента типичный containing block — viewport, но трансформации и ряд других свойств предка способны изменить это поведение.
  • Для процентов по вертикальному размеру важно, определён ли соответствующий размер containing block. Если он зависит от содержимого, процент иногда разрешается как auto или по специальным правилам конкретного свойства.

Позиционирование не меняет одну и ту же вещь

Static / normal flow

Бокс участвует в обычном потоке. Его положение зависит от предыдущих элементов, родительского formatting context и размеров соседей.

Relative

Сначала бокс занимает место так, как будто остаётся в потоке; затем его визуальное положение смещается. Исходное место сохраняется.

Absolute

Бокс исключается из normal flow и позиционируется относительно containing block. Он не резервирует место для себя в обычном потоке.

Fixed

Обычно привязан к viewport и не движется при обычной прокрутке документа. Но containing block может быть создан предком.

Sticky

Сочетает нормальный поток и ограничения прокрутки: положение становится «прилипшим» в пределах подходящего scroll container и containing block.

Float

Бокс выходит из обычного последовательного размещения, а inline content обтекает его. Это не аналог flex alignment и не способ задать произвольное позиционирование.

Физические и логические оси

Многие привычные объяснения оперируют left/right и width/height. Но CSS-компоновка должна поддерживать горизонтальное и вертикальное письмо, направления inline и block, RTL и смешанные writing modes. Логические свойства inline-size, block-size, margin-inline и inset-block-start описывают оси относительно writing mode, а физические свойства — относительно экрана.

Внутри движка физическая и логическая геометрия могут преобразовываться друг в друга. Не предполагай, что inline всегда означает горизонталь, а block — вертикаль.

05 · SIZING CONSTRAINTS

Как алгоритм получает итоговый размер

Размер бокса не всегда получается из одного свойства width. Алгоритм учитывает доступное пространство, preferred size, min/max constraints, intrinsic contributions содержимого, box sizing, aspect ratio и модель компоновки родителя.

Content box и border box

В стандартной модели box-sizing: content-box заданная ширина относится к content box. Padding и border добавляются снаружи. При border-box указанная ширина включает content, padding и border (но не margin). Это влияет на разрешение ограничений, но не меняет само понятие containing block или форматирование текста.

border-box inline size = content size + padding-inline + border-inlineДля горизонтальной физической модели; в логической записи рассматривается соответствующая inline axis.

Intrinsic sizes: min-content и max-content

Intrinsic sizing отвечает на вопрос: насколько содержимое хочет быть широким, если не учитывать обычный фиксированный размер родителя?

РазмерСмыслИнтуитивная проверка
min-contentНаименьший размер, который допускает содержимое при наиболее интенсивном разрешённом переносе.Для обычного текста часто близок к ширине самого длинного непереносимого фрагмента.
max-contentРазмер без soft wrapping в рассматриваемой оси, если нет иных ограничений.Длина содержимого в одну строку (с учётом реальной типографики).
fit-contentОграничивает размер доступным пространством, не опускаясь ниже min-content и не превышая max-content.Содержимое растёт, пока есть место, но не становится меньше своей минимальной intrinsic ширины.
fit-content(available) = min(max-content, max(min-content, available))Схематическая формула для понимания fit-content sizing; точное применение определяется конкретным свойством и алгоритмом.

Intrinsic contributions используются не только при явном width: min-content. Они участвуют в sizing flex/grid tracks, shrink-to-fit-подобных вычислениях, автоматических minimum sizes и других алгоритмах.

Почему percentage иногда «не работает как ожидалось»

Процент требует базы, относительно которой его можно вычислить. Если размер containing block по этой оси определён явно или может быть разрешён, процент обычно становится конкретным размером. Если размер зависит от потомков, возникает циклическая зависимость: размер родителя зависит от дочернего, а размер дочернего задан процентом от родителя. CSS определяет специальные правила для таких случаев; универсального правила «процент всегда от родителя» недостаточно.

min/max и автоматические минимумы

Окончательный размер ограничивается min-width/max-width (или логическими аналогами). В flex и grid автоматический минимум некоторых items может опираться на min-content contribution. Из-за этого item иногда не сжимается, хотя свободного места недостаточно. min-width: 0 в соответствующей горизонтальной модели разрешает ему стать уже intrinsic minimum; однако содержимое ещё может переполнять item, поэтому иногда дополнительно нужен перенос текста, clipping или scrolling.

Aspect ratio и replaced elements

Предпочтительное соотношение сторон (aspect-ratio) связывает размеры двух осей. Если одна ось определена, алгоритм может вывести другую с учётом min/max constraints и правил конкретного контекста. У replaced elements — например, изображений и видео — могут быть собственные intrinsic width, height и aspect ratio; CSS constraints могут ограничить или изменить их использованный размер.

Computed value ≠ used geometry

getComputedStyle() часто возвращает сериализованное resolved value, которое для отдельных свойств может быть уже использованным значением. Это не делает computed style универсальным источником всех размеров layout. Для геометрии конкретного элемента нужны соответствующие DOM geometry APIs и понимание их координатной системы.

06 · LAYOUT ALGORITHMS

Отдельные модели — отдельные алгоритмы

CSS задаёт несколько layout-моделей, каждая со своим алгоритмом. Движок не применяет один общий метод «положить детей в контейнер»: он выбирает поведение по formatting context и стилям.

Block layout — последовательный поток

В простом block flow дочерние block-level боксы располагаются последовательно в block direction. Их размеры могут зависеть от available inline size, margins, padding, borders и содержимого. Изменение ширины предка способно изменить переносы текста, а значит высоту потомков и положение следующих sibling boxes.

В блочной модели часто встречаются зависимости вверх/вниз по дереву и между соседями: сначала надо определить доступную ширину; после переноса строк становится известна высота; итоговая высота предыдущего блока сдвигает следующие. Поэтому изменение одного значения может инвалидировать существенную часть геометрии ниже по потоку.

Inline layout — построение строк

Упрощённо line layout включает следующие задачи:

  1. Сформировать последовательность inline items из текста, inline-боксов и специальных элементов.
  2. Определить shaping и метрики текста с учётом шрифтов, языка, bidi и writing mode.
  3. Найти допустимые точки переноса строки и выбрать переносы в пределах доступной ширины.
  4. Сформировать line boxes и согласовать вертикальное выравнивание фрагментов.
  5. Повторить для оставшегося текста, пока содержимое не будет размещено.

Это не буквальная реализация одного и того же внутреннего цикла в каждом браузере. Это описание основных задач. Реальные Unicode shaping и line breaking значительно сложнее: важны языковые правила, grapheme clusters, bidi reordering, hyphenation, fallback fonts и inline decorations.

Flexbox — распределение свободного пространства

Flex layout часто объясняют как распределение остатка ширины. Это лишь часть алгоритма. Для каждого item вычисляются flex base size и hypothetical main size; затем алгоритм определяет, будет ли контейнер распределять положительное или отрицательное свободное пространство, учитывает flex-grow или flex-shrink, min/max constraints и фиксирует («замораживает») items, которые достигли ограничений. В процессе могут повторяться этапы распределения.

1. ОсноваОпределить flex base size с учётом flex-basis и правил intrinsic sizing.
2. ГипотезаОграничить размер и получить hypothetical main size.
3. Свободное местоСопоставить суммарные размеры items с внутренним размером контейнера.
4. Grow или shrinkРаспределить положительное/отрицательное пространство с соответствующими коэффициентами.
5. Min/max и freezeОграничить нарушившие min/max items и повторно распределить остаток при необходимости.

При shrink учитывается scaled flex shrink factor, связанный с flex base size. Поэтому простое распределение отрицательного пространства только по значениям flex-shrink неверно.

Grid — алгоритм размеров tracks

Grid задаёт tracks, а алгоритм должен вычислить их базовые размеры и пределы роста. На sizing влияют фиксированные размеры, intrinsic track sizing functions (min-content, max-content, auto), spanning items, свободное пространство и flexible tracks (fr). В общем случае размер дорожки нельзя получить простым делением контейнера на число колонок.

  • Сначала определяется размещение items и набор tracks, включая неявные дорожки.
  • Затем вычисляются intrinsic contributions элементов, в том числе тех, которые перекрывают несколько tracks.
  • Track sizing algorithm устанавливает базовые размеры и growth limits и распределяет вклад содержимого.
  • После разрешения intrinsic размеров учитывается доступное свободное пространство и flexible tracks.
  • Ограничения контейнера, gutters, min/max и процентные размеры могут изменить результат.

Именно поэтому 1fr означает не просто «одну равную долю viewport». Это flexible track sizing function, работающая внутри конкретного grid container после соответствующих этапов sizing.

Flexbox и Grid на практике: min-width:auto

У flex item автоматический минимальный размер может не позволять сжаться уже min-content size. Частый исправляющий приём — min-width: 0 (или логический эквивалент по inline axis). Это не магический фикс: он снимает minimum constraint, но не гарантирует, что потомки будут красиво переноситься или обрезаться.

07 · FRAGMENTATION

Один бокс может превратиться в несколько фрагментов

Нельзя всегда представить результат layout одним прямоугольником на каждую DOM-ноду. Текст распадается на line fragments; многоколоночный контейнер и печатная страница дробят содержимое на fragmentainers; крупный элемент может продолжиться в следующей колонке или на следующей странице согласно правилам fragmentation.

Фрагментация встречается при печати, CSS Columns и в некоторых paged media сценариях. Учитываются свойства break-before/after/inside, доступное пространство, widows/orphans, keep constraints и правила конкретного алгоритма. Иногда перенос невозможен без нарушения ограничений, и движку приходится применять определённые стандартом fallback-поведения.

Fragment tree в Chromium LayoutNG

В LayoutNG Chromium layout algorithm производит immutable fragment results. Это отличается от старого подхода, где изменяемые layout objects долго хранили геометрию и помечались dirty. Fragment tree удобен для частичного переиспользования результатов, painting, hit-testing и фрагментации: один layout object способен соответствовать нескольким physical fragments, а некоторые fragmentainers не обязаны иметь отдельный обычный layout object.

Для некоторых моделей (в частности, flex и grid) движку может понадобиться отдельный measure pass, чтобы определить размеры содержимого, прежде чем выполнить финальную раскладку. Если вложенные измерения повторяются без кэширования, стоимость может резко расти. В LayoutNG явные объекты входных constraints и выходных fragments позволяют хранить и переиспользовать результаты измерения и layout. Это конкретное архитектурное решение Blink, а не обещание, что любой flex/grid layout в любом браузере имеет фиксированную сложность O(n).

Архитектура LayoutNG — деталь Blink/Chromium, а не нормативное требование CSS. Другие движки могут организовывать внутренние данные иначе, сохраняя веб-совместимое поведение.

08 · INCREMENTAL LAYOUT

Почему после изменения не всегда пересчитывается вся страница

Полная компоновка всего документа после каждого небольшого изменения была бы слишком дорогой. Движки отслеживают затронутые участки и стараются переиспользовать результаты там, где входные параметры не изменились. В разных движках это может называться dirty flags, invalidation, layout roots, constraints, fragment caching и по-другому.

Что может инвалидировать геометрию

  • Изменение размеров контейнера или viewport.
  • Изменение текста, шрифта, font loading, line-height или языковых настроек.
  • Добавление/удаление DOM-узлов, изменение классов и CSS-свойств, влияющих на layout.
  • Изменение контента изображения или replaced element, например после загрузки intrinsic dimensions.
  • Изменение grid/flex контекста, позиции, writing mode, scrollbar или scroll container.
  • События, связанные с viewport, zoom и доступным размером области отображения.

Зависимости ширины и высоты

Например, изменение inline-size родителя может привести к новым переносам строк, изменению block-size абзацев, сдвигу всех следующих блоков и изменению размеров scrollable overflow area. Поэтому влияние может распространяться дальше изменённого элемента. Обратная зависимость тоже возможна: intrinsic sizing дочерних элементов влияет на размеры родителя.

Containment — явная граница для части зависимостей

CSS Containment позволяет автору сообщить браузеру, что определённые части rendering/layout могут быть изолированы. contain: layout ограничивает некоторые связи layout с внешним окружением; contain: size меняет участие внутреннего содержимого в вычислении размера; contain: paint ограничивает область рисования; content-visibility: auto позволяет пропускать часть работы для содержимого вне области видимости при соблюдении правил intrinsic placeholder sizing.

Containment влияет и на поведение документа: новые containing blocks, stacking contexts, clipping, размеры и наблюдаемость. Это не бесплатный атрибут «ускорить div». Используй его, когда структура действительно допускает такие границы.

Не обещай локальность без доказательств

Изменение одного CSS-свойства может повлиять на соседей, потомков или большие участки страницы. И наоборот, браузер может переиспользовать результаты, которые теоретически могли бы быть затронуты. Реальную область работы определяй профилированием, а не по названию свойства.

Когда чтение геометрии запускает layout

Если JavaScript изменил стиль, влияющий на геометрию, а затем синхронно запросил layout-dependent значение, браузеру может потребоваться немедленно выполнить style/layout, чтобы вернуть актуальный результат. Это часто называют forced synchronous layout или forced reflow. Сам вызов getBoundingClientRect() не всегда дорог: стоимость зависит от того, устарели ли данные, которые нужно вернуть.

10 · PERFORMANCE ENGINEERING

Как не создавать лишнюю работу Layout Engine

Layout thrashing: read → write → read → write

Проблемный шаблон — чередовать изменения геометрии и чтение геометрических значений внутри цикла. Каждое чтение после инвалидирующей записи может вынудить браузер синхронно обновить layout. Лучше разделять фазу измерений и фазу изменений: сначала собрать нужные значения, затем выполнить записи, не читая геометрию между ними.

// Риск: чередование write/read.
for (const item of items) {
  item.style.width = `${container.offsetWidth}px`;
  console.log(item.offsetHeight);
}

// Предпочтительнее: группировать чтения и записи.
const width = container.offsetWidth;
const heights = items.map(item => item.offsetHeight);
for (const item of items) {
  item.style.width = `${width}px`;
}

Второй пример иллюстрирует принцип batching, но не является универсальным рефакторингом любого алгоритма. Если следующая запись действительно зависит от результата измерения предыдущего элемента, нужно пересмотреть саму задачу, применить ResizeObserver или изменить архитектуру обновления.

Практические рычаги

Сокращай геометрические зависимости

Не создавай глубокие каскады размеров «родитель зависит от ребёнка, ребёнок от родителя» без необходимости. Уточняй размеры там, где это соответствует интерфейсу.

Группируй DOM reads/writes

Измеряй значения пакетно, затем меняй DOM/CSS. Не запускай forced layout из повторяющихся обработчиков без причины.

Используй подходящую модель

Grid/Flex могут выразить распределение, которое иначе пришлось бы вычислять вручную в JavaScript и обновлять многочисленными style writes.

Применяй containment осознанно

Ограничивай layout/paint dependencies для независимых виджетов, но проверяй влияние на размеры, позиционирование, clipping и stacking.

Смотри на реальные bottlenecks

Большой DOM не гарантирует медленный layout, а малый — быстрый. Важны конкретные алгоритмы, invalidation area, стили, шрифты и частота обновлений.

Не превращай transform в универсальный костыль

Transform часто полезен для анимации визуального перемещения, но не заменяет layout, когда нужно перераспределить пространство между соседями.

11 · ENGINEERING CHECKLIST

Как рассуждать о проблеме компоновки

При неожиданном расположении элемента полезно не подбирать CSS наугад, а пройти цепочку причин.

  1. Проверь box generation.Есть ли у элемента principal box? Не действует ли display: none, contents, pseudo content или anonymous wrapper?
  2. Определи formatting context.Кто размещает элемент: normal flow, inline formatting, flex, grid, table, float или out-of-flow positioning?
  3. Найди containing block.Относительно какого бокса разрешаются процентные размеры и координаты?
  4. Собери ограничения.Какие available size, min/max, intrinsic contributions, margins, padding, border и aspect ratio применяются?
  5. Проверь письменную модель.Какие writing-mode, direction и логические оси действуют?
  6. Измерь реальность.Сравни box model в DevTools с getBoundingClientRect(), offset/client/scroll dimensions.
  7. Проверь момент обновления.Не читаешь ли ты геометрию сразу после style/DOM write и не вызываешь forced layout?
Инженерный вывод

Правильная компоновка — результат согласования модели CSS, содержимого и ограничений. Хорошее решение сначала устраняет неверную модель или constraint, а уже потом подбирает значения отступов и позиционирования.
