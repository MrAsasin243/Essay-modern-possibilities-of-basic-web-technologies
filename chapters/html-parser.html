HTML Parser: как браузер строит DOM

HTML-парсер — не регулярное выражение и не проверка вложенности тегов. Это нормативно описанный потоковый алгоритм: он декодирует вход, выдаёт токены конечным автоматом, а затем по состоянию документа изменяет DOM-дерево. Именно поэтому некорректный HTML часто не приводит к остановке разбора, а преобразуется в вполне определённую структуру.

Два связанных алгоритма

Tokenizer создаёт токены, Tree Builder интерпретирует их в контексте текущего состояния документа.

02

Ошибки имеют правила

03

Parser-inserted scripts, document.write() и потоковая загрузка делают разбор реентерабельным и управляемым.

Границы применимости

Алгоритмы этой главы относятся к разбору HTML-синтаксиса, прежде всего ресурсов с MIME type text/html. XML/XHTML использует XML parsing rules. Внутренние классы, потоки и оптимизации Blink, Gecko и WebKit — детали реализаций, а не обязательные имена объектов из стандарта.

01 · PARSING MODEL

HTML Parser — последовательность преобразований, а не один проход по тегам

Для сетевого документа браузер получает байты. Чтобы построить DOM, нужно определить кодировку, превратить байты в поток кодовых точек, обработать окончания строк, распознать HTML-токены и применить к ним правила построения дерева. В реальном браузере загрузка следующего фрагмента данных, предварительное обнаружение ресурсов и выполнение скриптов могут перекрываться по времени с разбором.

Input bytesNetwork / document source
Byte stream decoderОпределение кодировки и декодирование
Input preprocessingНормализация входного потока
TokenizerПоток токенов
Tree constructionInsertion mode + parser state
DOM DocumentДерево узлов

Концептуальная схема последовательности обработки. Это не означает, что каждый блок обязательно реализован как отдельный поток или самостоятельный объект движка.

Два алгоритма работают совместно

A

Tokenizer

Читает поток кодовых точек и поддерживает текущее состояние. Он распознаёт начала тегов, имена тегов, атрибуты, комментарии, DOCTYPE, символьные ссылки и специальные текстовые режимы. Результат — токены, а не DOM-узлы.

B

Tree construction

Получает токены и выбирает правила их обработки по текущему insertion mode, стеку открытых элементов, списку активных форматирующих элементов и другим указателям. Алгоритм вставляет, перемещает, закрывает и иногда повторно создаёт DOM-элементы.

C

Parser state

Состояние не сводится к одному стеку. Есть insertion mode, original insertion mode, template insertion modes, stack of open elements, active formatting elements, form/head pointers, scripting flag и дополнительные флаги.

Почему это не XML?

HTML имеет собственные правила токенизации и восстановления дерева. XML-парсер работает по другой модели: например, ошибка well-formedness обычно является фатальной для XML-документа, тогда как HTML parsing algorithm определяет обработку множества ошибочных последовательностей.

02 · INPUT STREAM

Входной поток: байты ещё не являются HTML-токенами

Сетевой слой передаёт байты тела ответа. Парсеру нужны символы, поэтому до tokenization выполняется декодирование. Кодировка может определяться по BOM, транспортной информации, декларации meta charset и fallback-правилам HTML/Encoding Standards. Это отдельная задача: tokenizer не должен угадывать UTF-8 или читать байты как готовые символы.

Важные стадии входа

СтадияВходЗадачаВозможный эффект

Preprocessing и символы

HTML input stream preprocessing нормализует carriage return: последовательность CRLF рассматривается как один LF, а одиночный CR также преобразуется в LF. Обработка U+0000 зависит от состояния tokenizer: во многих текстовых и атрибутных состояниях это parse error, после которого используется U+FFFD REPLACEMENT CHARACTER. Не следует смешивать правила декодера, preprocessing и tokenizer — это разные уровни.

Поток на границе tokenizerbytes → code points → normalized input → tokensДля fragment parsing исходные символы могут поступать из DOM API, а не из сетевого ответа.

Почему важна граница между chunks

Поток может закончиться посередине конструкции: после символа <, внутри имени атрибута или в quoted value. Это не означает, что токен завершён. Парсер сохраняет состояние и продолжает, когда получает следующую порцию. Только настоящий EOF запускает правила завершения незакрытой конструкции.

03 · TOKENIZATION

Tokenizer: конечный автомат, который выдаёт токены

Tokenizer последовательно потребляет кодовые точки. Его поведение описывается набором состояний. В одном состоянии символ может добавить данные к текущему токену, переключить состояние, вызвать reconsume — повторную обработку того же символа в новом состоянии — либо завершить токен и передать его Tree Builder.

Основные виды токенов

Start tagИмя, набор атрибутов, self-closing flag<img src="a.png">

Пример прохождения обычного start tag

<section class="card" data-state=ready>
  1. DataПолучен символ <; автомат переходит к распознаванию начала тега.
  2. Tag openПолучена ASCII-буква; создаётся start tag token, начинается имя тега.
  3. Tag nameСимволы section добавляются в имя. ASCII uppercase в именах HTML-тегов приводится к lowercase.
  4. Before attribute name / Attribute nameПосле пробела начинается атрибут class.
  5. Before attribute value / Double-quoted valueЗначение card считывается до закрывающей кавычки.
  6. Attribute name / Unquoted valueСледующий атрибут data-state получает значение ready без кавычек.
  7. Tag emissionПри > токен завершается и отправляется Tree Builder.
Повторяющиеся атрибуты

Если в start tag встречаются атрибуты с одинаковым именем, парсер сообщает parse error и игнорирует последующие повторы. DOM не обязан сохранять исходную последовательность как есть: например, <div id="first" id="second"> не создаёт два одноимённых атрибута.

Символьные ссылки — отдельная машина состояний

В тексте и значениях атрибутов символ & может запустить character reference state. Разрешаются named references (например, &amp;) и numeric references (например, &#x1F680;). Результат зависит от контекста возврата и набора правил, поэтому простая замена регулярным выражением неэквивалентна HTML tokenizer.

04 · TOKENIZER STATES

Состояния tokenizer зависят от контекста

В стандарте намного больше состояний, чем «текст», «тег» и «атрибут». В частности, содержимое разных элементов разбирается в разных режимах: title и textarea используют RCDATA, style и часть других элементов — RAWTEXT, а script имеет собственное семейство script data states.

Почему состояние зависит от Tree Builder

Tokenizer и Tree Builder — не независимые чёрные ящики. При обработке start tag для script, style, title и других элементов Tree Builder может переключить tokenizer в соответствующее текстовое состояние. Контекст текущего элемента изменяет трактовку одних и тех же символов.

05 · TREE CONSTRUCTION

Tree construction: один токен может менять множество узлов

Tree Builder принимает очередной токен и применяет правила выбранного insertion mode. Это не механическое правило «start tag — append child, end tag — удалить родителя». В зависимости от токена алгоритм может создать неявный элемент, закрыть предыдущий элемент, переместить узел, проигнорировать токен, сменить insertion mode и повторно обработать тот же токен.

Главные структуры состояния

Stack of open elements

Стек открытых элементов отражает путь от корневого html к текущему узлу. Его верхушка обычно соответствует current node. Это не всегда то же самое, что цепочка DOM-родителей: алгоритмы форматирования и перемещения узлов могут временно разносить эти представления.

Active formatting elements

Список хранит определённые форматирующие элементы, например b, i и font. Он позволяет восстановить форматирование после некоторых ошибочных последовательностей и не совпадает со стеком открытых элементов.

Insertion mode

Переменная задаёт, какой набор правил используется для текущего токена: например, in head, in body, in table, in row или in cell.

Дополнительные указатели

Tree Builder хранит head/form element pointers, template insertion mode stack, original insertion mode, frameset-ok flag и иные состояния, необходимые конкретным правилам.

Insertion modes — таблица правил, а не визуальные этапы

В WHATWG HTML определена последовательность режимов вставки. Они не означают, что парсер проходит через них все один раз. Режим меняется по мере поступления токенов; некоторые режимы передают обработку правилам другого режима, сохраняя или изменяя состояние по правилам алгоритма.

Начальное состояние документа и DOCTYPE

В режиме initial Tree Builder обрабатывает начальные пробельные символы, комментарии и DOCTYPE. Корректно расположенный современный <!DOCTYPE html> переводит документ в no-quirks mode. Некоторые исторические DOCTYPE и отдельные ошибочные случаи могут включить quirks mode или limited-quirks mode. Если DOCTYPE отсутствует или распознан как force-quirks, результат также определяется правилами этой начальной стадии.

Затем алгоритм переходит через before html, before head и in head. Если исходник не содержит явных html или head, необходимые элементы создаются неявно. После завершения head-поддерева парсер переходит к after head, а при необходимости создаёт body и обрабатывает токены в in body.

<!doctype html>
<title>Document title</title>
<main>Content</main>

DOM outline (conceptual)
Document
├─ DocumentType: html
└─ html
   ├─ head
   │  └─ title
   └─ body
      └─ main

Свойство document.compatMode различает BackCompat (quirks) и CSS1Compat (no-quirks и limited-quirks). Поэтому по одному значению CSS1Compat нельзя определить, какой из двух последних режимов установлен.

Пример: автоматическое закрытие p

<p>Первый абзац
<p>Второй абзац

Когда Tree Builder в режиме in body получает второй start tag p, а предыдущий p находится в button scope, алгоритм закрывает предыдущий абзац перед вставкой нового. Явный </p> перед вторым тегом не требуется, чтобы получить два соседних абзаца.

Reprocess — повторная обработка токена

Некоторые правила сначала закрывают текущий контекст, меняют insertion mode, а затем требуют reprocess текущего токена. Это позволяет, например, встретить токен tr в режиме in table, подготовить контекст тела таблицы и обработать тот же tr уже в новом режиме. В алгоритме нельзя терять токен, который потребовал переключения режима.

06 · ERROR RECOVERY

Восстановление ошибок — часть алгоритма HTML

Parse error — термин спецификации для определённого ошибочного состояния входа. Он не означает автоматически исключение JavaScript, сетевую ошибку или обязательную остановку браузера. Для многих parse errors стандарт задаёт детерминированное восстановительное поведение: проигнорировать токен, вставить или переместить узел, закрыть элемент, изменить место вставки либо продолжить разбор. При этом стандарт допускает, что user agent может прервать parsing при parse error, если не применяет предусмотренные правила восстановления; обычные браузеры ориентированы на совместимую обработку ошибочной разметки.

Implied end tags

В некоторых контекстах парсер генерирует implied end tags: он закрывает элементы из определённого набора без отдельного end-tag token в исходном HTML. Это применяется, например, при закрытии абзацев, элементов списка и ряда структурных элементов. Алгоритм всё равно проверяет границы scope, поэтому нельзя свести его к правилу «любой открытый тег закрывается следующим тегом».

Active formatting elements и reconstruction

Список активных форматирующих элементов нужен для обработки вложенности вроде b и i. Когда дальнейший токен требует восстановить форматирование, алгоритм может заново создать элементы в DOM и связать их с текущим контекстом. Поэтому дерево DOM не обязано повторять буквальную вложенность исходных start/end tags.

Adoption Agency Algorithm

Для определённой группы форматирующих end tags используется специальный алгоритм восстановления. Он ищет formatting element в active formatting elements, определяет furthest block и common ancestor, затем по заданным правилам перемещает и переиспользует узлы, при необходимости создаёт новые элементы. Это не просто «закрыть все теги до совпавшего»; алгоритм исторически сложен, но обеспечивает согласованное DOM-представление распространённой некорректной разметки.

<p>1<b>2<i>3</b>4</i>5</p>

После обработки </b> парсер должен восстановить структуру форматирования так, чтобы последующий текст сохранил требуемую семантику вложенности. Точный результат следует смотреть в DOM-дереве браузера, а не выводить только по исходному тексту.

Foster parenting: содержимое внутри table

Если parser обрабатывает содержимое в табличном контексте и включён foster parenting, некоторые ошибочно размещённые узлы вставляются не внутрь таблицы, а перед ближайшей подходящей таблицей или в соответствующий родительский узел. Это правило предотвращает попадание произвольного содержимого в места, где табличная структура требует специальных элементов.

<table>
  outside text
  <tr><td>cell</td></tr>
</table>

Текст outside text не обязан стать обычным дочерним текстовым узлом table. Результат зависит от табличного режима, pending table character tokens и алгоритма вставки.

Scope и foreign content

Для поиска и закрытия элементов используются разные виды scope — например, button scope, list item scope и table scope. Они ограничивают поиск структурными границами. При встрече SVG/MathML парсер применяет правила foreign content, а точки интеграции позволяют в определённых случаях вернуться к правилам HTML. HTML tokenizer и Tree Builder также выполняют корректировку имён некоторых элементов и атрибутов в foreign namespaces.

Parse errors не равны ошибкам соответствия вообще

Conformance checker проверяет не только parse errors, но и остальные требования HTML. Валидность документа, восстановление DOM и успешное отображение — три разные характеристики. Обычный браузерный JavaScript API не предоставляет универсальный список всех parse errors, найденных парсером при загрузке страницы.

07 · SCRIPT EXECUTION

Scripts могут приостанавливать и возобновлять парсер

HTML parsing связан с исполнением скриптов. Обычный parser-inserted classic script без async или defer может быть parser-blocking: парсер доходит до элемента, должен дождаться загрузки скрипта (если он внешний) и выполнить его перед продолжением разбора. Причина — скрипт может синхронно читать или менять документ, в том числе влиять на входной поток через document.write().

Classic deferЗагружается параллельно; выполняется после завершения разбора, с сохранением порядка defer scriptsНе блокирует parsing, но участвует в завершении этапа перед DOMContentLoaded
Classic asyncВыполняется, когда файл готов; порядок между такими скриптами не гарантированНе ждёт окончания parsing, но выполнение может прервать основной поток в момент запуска

Динамически созданный scriptПоведение зависит от способа создания, атрибутов и force-async stateНе следует автоматически приравнивать к parser-inserted script

Реентерабельность и document.write()

Tree construction может быть реентерабельным. Пока обрабатывается один токен, выполняется скрипт; вызов document.write() добавляет символы во входной поток, и tokenizer может быть возобновлён, чтобы выдать новые токены до завершения внешней обработки. Для этого модель парсера содержит script nesting level и parser pause flag. Поэтому «HTML сначала целиком разбирается, затем запускается JavaScript» неверно.

Preload scanner — оптимизация реализации

Chromium и другие браузеры могут предварительно просматривать доступную часть HTML, чтобы начать загрузку ресурсов, пока основной parser ожидает блокирующий скрипт. Это не самостоятельный нормативный этап, который обязательно обязан существовать как отдельный scanner. Предварительный сканер не заменяет Tree Builder и не гарантирует обнаружение ресурсов, которые появятся только после выполнения JavaScript.

Связь с событиями документа

document.readyState, DOMContentLoaded и load отражают разные точки жизненного цикла. Завершение parsing — не то же самое, что загрузка всех зависимых ресурсов. Defer/module scripts и stylesheet dependencies влияют на момент событий по правилам HTML Standard. Эти события не говорят, что все изображения уже декодированы или что пользовательский интерфейс полностью стабилизировался.

08 · FRAGMENT PARSING

Fragment parsing: разбор зависит от контекстного элемента

HTML fragment parsing применяется, когда нужно разобрать фрагмент с учётом контекста. Например, присваивание element.innerHTML не равнозначно загрузке полного HTML-документа. Контекстный элемент влияет на начальный tokenizer state и на то, какие правила Tree Builder применяются. Это особенно заметно для table, tbody, select, textarea и элементов с особым текстовым режимом.

Fragment parsingcontext element + fragment source → fragment nodesРезультат затем используется DOM API вызывающего контекста.

Примеры API, которые задействуют HTML fragment parsing в определённом контексте: Element.innerHTML, Range.createContextualFragment() и операции, определённые через fragment parsing. Конкретные API могут добавлять собственные проверки безопасности и sanitizer-конфигурацию.

DOMParser и innerHTML — не взаимозаменяемы

DOMParser.parseFromString(source, "text/html") создаёт отдельный Document и разбирает полный документ. innerHTML использует контекст существующего элемента. Если нужно воспроизвести поведение таблицы, select или textarea, меняй контекст лаборатории, а не только саму строку.

09 · STREAMING AND COMPLETION

Потоковый и инкрементальный разбор

Сетевой ответ может поступать частями. Парсер способен обрабатывать уже доступный фрагмент, не ожидая полного HTML-файла. При этом tokenizer сохраняет незавершённое состояние: начало тега, имя атрибута, значение или комментарий могут продолжиться в следующем chunk. Если возникает parser-blocking script, основной разбор может приостановиться, а после разрешения блокировки продолжиться с сохранённого состояния.

Что не следует путать

ПонятиеЧто означаетЧем не является
Incremental parsingОбработка входа по мере поступленияНе означает, что DOM всегда сразу отображается без задержек
Preload scanningПредварительное обнаружение вероятных ресурсовНе заменяет нормативную tokenization/tree construction

Потоковый разбор важен для времени до первого содержимого и загрузки критических ресурсов, но на практике его эффект зависит от порядка ресурсов, блокирующих скриптов, таблиц стилей, задержек сети и того, когда браузер получает достаточно данных для построения полезной части документа.

10 · ENGINE IMPLEMENTATIONS

Что общее у стандартов и что различается в движках

HTML Standard определяет наблюдаемый алгоритм построения DOM из HTML. Он не требует от браузеров одинаковых названий классов, структуры потоков, архитектуры очередей или конкретной организации памяти. Реальные реализации имеют свои парсеры и оптимизации.

СемействоРеализацияЧто изучать в исходниках
Chromium / BlinkBlink HTMLDocumentParser, HTMLTokenizer, HTMLTreeBuilder и связанные script/preload componentsПотоковый ввод, паузы для scripts, preload scanner, deferred parsing и взаимодействие с renderer lifecycle
Firefox / GeckoGecko HTML parser, который реализует HTML parsing model и интегрирован с DOM/GeckoTokenizer/tree builder, parser threading/dispatch и взаимодействие с content process
WebKitHTML parsing в WebCoreHTMLDocumentParser/HTMLTreeBuilder, tokenizer и связь с WebCore DOM

Сравнивать реализации нужно по конкретным задачам и версиям исходников. Нельзя делать вывод, что наличие класса с похожим именем означает одинаковую архитектуру или одинаковый порядок внутренних вызовов.

Метод чтения исходников

  1. Начни с точки входа парсера документа и проследи, откуда поступают новые байты/символы.
  2. Найди tokenizer и tree builder, затем сопоставь их интерфейсы с разделами WHATWG.
  3. Найди обработку parser-blocking scripts, parser pause/resume и fragment parsing.
  4. Отдельно исследуй preload scanning и scheduling: это оптимизации реализации, не алгоритм построения DOM.
  5. Подтверди предположение тестом WPT или небольшим воспроизводимым HTML примером.
